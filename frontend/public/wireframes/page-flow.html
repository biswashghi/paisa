Product architecture

Partner admin page and input flow

A proposed portal map for how partner admins move from setup to enrollment, member-specific rewards changes, earned activity review, and operational audit.

Open Mermaid source
01 Workspace Entry Establish partner, environment, and operating context.

Sign In / SSO

Inputs
Email, auth method, partner workspace, API environment.
Outputs
Authenticated admin context and default workspace.

Command Center

Inputs
Date range, selected programs, rule health, exception queue.
Outputs
Prioritized worklist: setup, member actions, activity audit, exports.
02 Program Setup Create the rewards container before enrolling members.

Program Builder

Inputs
Name, earn currency, liability model, enrollment policy, effective dates.
Outputs
Draft program with policy and accounting defaults.

Program Detail

Inputs
Program metadata, status, policy, active base rules, package library.
Outputs
Program ready for enrollment, rule editing, package creation, and audit.

Rule Studio

Inputs
Applies-to scope, group strategy, eligibility, formula, caps, dependencies, tests.
Outputs
Validated base rule version or reusable member add-on package.

Publish / Schedule

Inputs
Validation result, publish date, change note, reviewer.
Outputs
Active base rule or published add-on package available to assign.
03 Enrollment And Member Operations Put members into programs, then layer exceptions carefully.

Enrollment Inbox

Inputs
API imports, CSV uploads, invitations, consent, eligibility review.
Outputs
Approved, pending, or rejected member enrollments.

Member Rewards Profile

Inputs
Member lookup, active program, balance, add-ons, earning history.
Outputs
Decision point for move program, add package, adjustment, or audit.

Move Program

Inputs
Target program, effective date, reason, operator note.
Outputs
New active enrollment and preserved historical trace.

Assign Add-On Package

Inputs
Published package, start/end dates, reason, compatibility check.
Outputs
Active member rule assignment layered over base program.
04 Earned Activity And Simulation Explain points before and after transactions post.

Rule Simulator

Inputs
Member profile, hypothetical transaction, date, category, amount.
Outputs
Projected points, rule explanation, validation feedback.

Transaction Review

Inputs
Transaction id, member, program, category, amount, event time.
Outputs
Earning trace showing base rule and add-on package sources.

Ledger And Liability

Inputs
Posted earns, burns, reversals, adjustments, liability period.
Outputs
Balance, liability accrual, reconciliation totals.
05 Audit, Exports, Integrations Close the loop with traceability and partner reporting.

Audit Log

Inputs
Rule publishes, member moves, package assignments, manual adjustments.
Outputs
Operator trace, compliance history, rollback context.

Exports And Webhooks

Inputs
Date range, file schema, destination, webhook retry policy.
Outputs
Partner files, callbacks, and integration delivery status.

Health And Exceptions

Inputs
Failed validations, processing errors, stale exports, unusual liability changes.
Outputs
Command Center alerts and next action queue.

Flow rules

How pages hand work to each other

Programs come before members.A member cannot enroll until a program has policy and at least one publishable base rule path.
Rules publish into scopes.Rule Studio publishes either a program base rule or a reusable add-on package, never an ambiguous private copy.
Member actions require reason and effective timing.Move program and assign package both create auditable changes that affect future earning.
Transactions always explain source.Earned activity should show base rule, add-on package, simulation result, ledger entry, and audit event.
Exceptions return to the Command Center.Failed validations, export retries, and processing anomalies become dashboard work items.
